# 统一联网搜索与模型搜索后端

## 背景

Nekusora 当前在聊天请求开始前直接调用首个已启用的外接搜索 Provider，并把结果注入 system prompt。该行为存在四个核心问题：

- 联网开关开启后每轮都会搜索，主模型不能按问题需要决定是否搜索。
- 只使用首个 Provider，没有用户级的统一后端排序、跨后端降级或模型代搜。
- GPT、Claude、Gemini、Grok 等模型的原生搜索没有统一能力目录与执行契约。
- 密钥明文下发、SearXNG SSRF、搜索结果不持久化等问题使现状不适合继续扩展。

本任务把联网能力收敛为一个用户可控、模型按需调用、服务端统一路由的搜索系统。

## 目标

当聊天中的单一“联网”开关开启时，主模型根据用户问题自行决定是否调用搜索；一旦调用，Nekusora 按该用户的全局后端顺序选择当前模型原生搜索、指定模型代搜或外接搜索 Provider，并把可追溯的引用交还主模型生成最终回答。

## 已确认决策

- 搜索按需触发，不因联网开关开启而在每轮预搜索。
- 搜索后端采用用户级全局排序，聊天界面仍只保留一个联网开关。
- 会话只持久化联网开关，不持久化某个搜索后端。
- 主模型决定“是否搜索、搜索什么”；Nekusora 决定“哪个后端执行”。
- 主模型只获得一个逻辑搜索能力，不同时看到 Tavily、SearXNG、GPT、Grok 等多个搜索工具。
- 指定搜索模型只返回 grounded summary 与 citations，最终回答仍由当前主模型生成。
- SearXNG 必须配置公网 HTTP/HTTPS 地址；私网、环回、本地域名、Docker 服务名及跳转到私网均拒绝。
- `/v1` 网关不做隐式搜索，只处理客户端明确传入的工具或协议字段。
- 对既无工具调用能力、又无可用原生搜索路径的模型，第一版不承诺按需搜索。
- 旧用户沿用现有已启用外接 Provider 的相对顺序，并在末尾追加“当前模型”；新用户默认仅有“当前模型”。

## 功能要求

### 1. 聊天体验

- 聊天输入区只保留一个联网开关，不增加聊天级 Provider/模型选择器。
- 请求显式携带布尔开关时以本轮值为准；请求未携带时回退到会话已保存值，不能因刷新或非标准发送路径静默关闭联网。
- 联网关闭时不得暴露搜索工具、发起搜索请求或产生搜索事件。
- 联网开启时只暴露一个逻辑搜索能力，由主模型按需调用；不得通过关键词分类器或每轮预请求强制搜索。
- 搜索开始、成功、失败均应在当前 assistant 消息中形成可恢复的状态。
- 成功结果必须显示来源；引用 URL 必须经过服务端校验，并在界面中清晰、可点击。
- 所有搜索后端失败时，主模型收到结构化失败结果，不得把失败伪装成已联网或基于旧知识编造实时事实。

### 2. 用户级全局后端顺序

- 用户可在联网搜索设置页维护一份全局有序列表。
- 列表支持三类条目：
  - 当前模型原生搜索。
  - 指定模型代搜，包括目录中明确支持搜索且用户有权调用的 GPT、Claude、Gemini、Grok 等模型。
  - 外接 Provider：Tavily、Bocha、智谱、SearXNG。
- 排序对该用户的所有聊天生效；聊天或会话不得覆盖该顺序。
- 运行时按顺序跳过不可用条目，并在可重试失败、空结果或无有效引用时尝试后续条目。
- 用户删除、禁用或失去某个 Provider/模型权限后，后续聊天不得继续使用缓存中的旧后端。

### 3. 当前模型与模型代搜

- 模型是否支持原生搜索，只能读取 `model_catalog` 中的显式能力数据，不按模型名、厂商名或 URL 猜测。
- 第一版支持 OpenAI、Anthropic、Google、xAI 四种原生搜索格式。
- “当前模型”条目使用当前聊天模型及其本轮已解析的可用路由执行原生搜索。
- “指定模型”条目使用用户有权访问的指定模型执行独立搜索请求。
- 搜索模型不得继承主聊天的 MCP 工具或逻辑 `web_search`，避免递归搜索和越权工具调用。
- 搜索模型结果没有有效引用时视为失败，可继续尝试后续后端。
- 搜索模型的调用、用量、耗时与最终主回答归属于同一个外层聊天 run，并可追溯到具体搜索调用。

### 4. 外接 Provider

- 保留 Tavily、Bocha、智谱、SearXNG，并统一输出标题、URL、摘要等最小公共结构。
- 每次搜索必须受外层取消信号与总时限控制；超时后不得继续遗留请求。
- 只对明确的临时网络错误、限流和 5xx 做有限重试；认证、配置和响应格式错误不得盲目重试。
- 外部响应必须在边界经过结构校验、URL 过滤、去重、数量与文本长度限制。
- 搜索摘要和网页片段均视为不可信内容，不得作为系统指令执行。

### 5. 配置与安全

- 已保存的搜索 API key 必须加密存储，服务端仅在执行请求时解密。
- 客户端 DTO 只能获得 `hasApiKey` 等脱敏状态，不得收到密文或完整明文。
- 编辑 Provider 时，空 key 表示保留原 key；替换 key 必须由服务端完成。
- 每个 Server Action 必须在执行体内重新鉴权，并以当前 session 用户作为唯一属主。
- SearXNG 保存与调用时都必须执行公网地址校验；DNS 解析、实际连接地址和每一跳重定向都不得落入非公网地址。
- 查询、密钥、搜索摘要不得写入 Prometheus 标签或普通应用日志；授权会话内的消息追踪可以保存必要查询与引用。

### 6. 持久化与恢复

- 搜索查询、执行模式、实际后端、状态、耗时和引用随 assistant 消息/run 持久化。
- 页面刷新、历史加载、回复版本切换、重新生成与继续生成后，搜索状态和引用必须与对应消息版本一致。
- 不新增独立引用表；优先扩展现有消息 `processTrace` JSONB 与现有 run/tool 记录链路。
- 旧消息没有搜索追踪字段时继续正常显示，不要求数据回填。

### 7. 兼容与迁移

- 现有 `user_settings.key = "web_search"` 配置必须可迁移，不得丢失 Provider 或改变旧用户外接 Provider 的相对顺序。
- 新写入配置不得继续保留明文 key；旧明文兼容只能作为有期限的迁移阶段。
- `model_catalog` 新增搜索能力数据时，必须提供 PostgreSQL 迁移、Drizzle journal/snapshot 同步及模型匹配测试。
- 内部 WebChat SSE 可以原子升级，但客户端不得把裸 EOF、失败或缺失搜索完成事件解释为成功。

## 非目标

- 网页正文抓取 `web_extract`、浏览器自动化或通用爬虫。
- Deep Research、多 query planner 或新的完整 Agent 引擎。
- 新增搜索引用关系表。
- 让搜索模型直接替代主模型输出最终回答。
- 在前端、route 或 Provider URL 层维护第二份模型搜索能力表。
- 为 `/v1` 请求自动添加用户未声明的搜索行为。

## 验收标准

- [ ] 联网关闭时零搜索请求；联网开启但问题不需实时信息时，支持工具调用的主模型可以不搜索。
- [ ] 请求值与会话值的回退规则有 route/store/action 测试，刷新和新会话 adopt 后开关保持一致。
- [ ] 主模型在一次 run 中只看到一个逻辑搜索工具，且能在需要时生成查询并消费结构化结果。
- [ ] GLM 等无原生搜索但支持工具调用的模型，可以按用户顺序委托 Grok、GPT、Gemini 或 Claude 搜索，再由 GLM 输出最终回答。
- [ ] 当前模型、指定模型和外接 Provider 可处于同一用户级有序列表，失败时按契约降级且不会重复向主模型暴露工具。
- [ ] `model_catalog` 是搜索能力唯一事实来源；未知或未标记模型不启用原生搜索。
- [ ] SearXNG 拒绝 localhost、私网 IPv4/IPv6、链路本地、云 metadata、单标签服务名、DNS 重绑定和重定向到私网；合法公网 HTTP/HTTPS 实例可用。
- [ ] 搜索密钥在数据库中为密文，页面源码/props/网络响应不含完整 key，Server Action 不信任渲染闭包中的 userId。
- [ ] 超时和取消能终止真实底层请求；有限重试、后端降级、响应校验、URL 去重均有测试。
- [ ] 搜索开始/成功/失败事件与引用能在刷新、历史加载和回复版本切换后恢复。
- [ ] 旧用户配置迁移后顺序兼容，新用户默认只有“当前模型”，旧消息无追踪字段仍兼容。
- [ ] `/v1` 未显式传入搜索工具时行为不变。
- [ ] 相关 lint、typecheck、单元测试、迁移一致性检查和构建门禁通过。

## 风险与约束

- Provider 原生搜索的事件格式不同，必须先归一化再进入 SSE、追踪和 UI。
- `current-model` 可能有目录能力但当前可用路由不支持对应原生协议，运行时必须跳过而不是猜测或伪造请求。
- 搜索密钥的历史明文无法仅靠 SQL 使用应用密钥加密，需要分阶段双读、新写密文、应用级回填与收口验证。
- 新增 xAI SDK 或协议适配必须与当前 AI SDK 7 依赖族兼容，并接受依赖安全审查。
