# 技术债修复总体设计

## Boundaries

父任务只维护范围、顺序和最终集成复核，不直接承载产品代码。五个子任务分别拥有模型目录、CI、存储、前端和工程清理，避免跨风险面混改。

## Execution Order

1. 模型目录一致性：先阻止错误能力继续进入目录，再迁移已有数据。
2. CI PostgreSQL：让后续数据库改动进入真实集成测试门禁。
3. 存储与 readiness：收紧生产数据落点和健康探针资源边界。
4. 前端债务：独立修复可访问性、状态和请求取消。
5. 工程清理：最后删除依赖与死代码，降低对前序改动的干扰。

## Cross-Task Contracts

- `model_catalog` 仍是模型能力唯一事实来源；前端和路由层不得新增能力判断。
- 模型数据修复通过新增 PostgreSQL 迁移落到已有数据库，并同步 Drizzle journal/snapshot。
- CI 数据库使用隔离随机库，禁止连接非本机测试数据库或删除不符合固定前缀的数据库。
- 显式远端存储配置失败必须报错；只有未配置或明确 `local` 才使用本地存储。
- 子任务只修改自身范围，最终由父任务统一检查全仓测试、构建和工作树差异。

## Rollback

- 每个子任务独立提交；出现回归时按子任务回滚，不交叉撤销其他修复。
- 模型迁移使用确定性、幂等 UPDATE；回滚前保留迁移前统计与生成证据，不修改已发布 baseline。
- CI、前端、脚本和代码删除均可通过对应子任务提交直接回滚。

## Risks

- 模型能力证据不足时宁可隐藏推理能力，不暴露不会生效的档位。
- PostgreSQL 集成测试会增加 CI 时间；仅运行真实数据库必需套件，不重复普通单测。
- readiness 无法强制取消所有第三方 promise；采用每类依赖单飞限制，保证超时后不会随探针次数无限累积。
