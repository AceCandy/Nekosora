# 持久化并展示聊天图片附件

## Goal

让用户发送图片后，图片成为用户消息的一部分：发送时立即显示，刷新后仍可恢复，并在编辑重发或重新生成时继续作为同一条用户输入的模型上下文使用。图片上传失败时不得静默退化为纯文本请求。

## Background

- 当前输入区能预览图片并上传为 `fileId`，首轮 `/api/chat` 请求也能把有效图片构造成多模态内容。
- `ChatMessage`、用户消息乐观状态、数据库消息投影和 `ChatMessageItem` 仍只有文本内容，因此发送后的用户气泡不显示图片，刷新后也无法恢复附件。
- 最近的 AI SDK 适配仅修复图片内容块的请求格式，明确未覆盖历史多模态消息的数据库序列化或恢复。

## Requirements

- R1：图片上传成功后，当前用户消息立即显示对应图片；文字与图片同属一条消息，保持现有消息顺序和分支语义。
- R2：图片附件必须与具体用户消息建立持久化关联；刷新、重新进入会话和切换分支后仍能恢复。
- R3：服务端必须以同一批经过所有权、会话归属和 MIME 校验的附件同时驱动消息持久化与首轮多模态模型请求，避免 UI 与模型上下文不一致。
- R4：任一待发送图片上传失败时阻止本轮发送，并在输入区显示可重试的本地化错误；不得继续发出不含图片的纯文本请求。
- R5：重新生成必须复用目标用户消息的图片附件；编辑重发默认继承原附件，并允许用户在提交前移除附件。
- R5a：允许不输入文字、只发送图片；编辑仅图片消息时，只要仍保留至少一张图片即可重发。
- R6：用户消息中的图片使用现有附件预览与图片查看器视觉语言；图片位于文字上方，支持加载、失败、键盘访问与点击无边框查看，不新增装饰性卡片或独立标题栏。
- R7：历史纯文本消息和缺少附件关联的旧消息必须继续正常显示和参与对话，不做历史数据回填。
- R8：附件展示 URL 必须在读取边界动态生成并执行当前用户鉴权，不持久化临时 object URL、签名 URL 或 base64 图片数据。
- R9：删除消息或会话时不得留下不可控的关联记录；文件对象的实际删除策略沿用现有文件生命周期，不因本任务扩大到知识库文件治理。
- R10：本任务不改变模型目录的 `capabilities.vision` 事实来源；不支持图片的模型继续在服务端明确拒绝图片请求。

## Acceptance Criteria

- [ ] AC1：发送一条“图片 + 文字”消息后，用户气泡立即显示图片和文字，模型首轮请求收到同一张图片。
- [ ] AC2：发送仅图片消息时允许提交并正常显示；现有纯文本消息行为不变。
- [ ] AC3：刷新页面或重新进入会话后，图片仍显示在原用户消息中，附件顺序稳定。
- [ ] AC4：图片上传失败时用户消息不会进入 store、数据库或 `/api/chat`，输入区显示错误并保留附件供重试或移除；新会话为取得上传归属而提前创建的空会话允许保留。
- [ ] AC5：重新生成时原用户消息的附件再次进入模型请求；编辑重发默认保留附件，移除后本次重发不再携带该附件；文字与附件都为空时禁止提交。
- [ ] AC6：附件查询按当前可见消息批量加载，不为每条消息产生独立查询；无权访问的文件不会生成展示 URL。
- [ ] AC7：用户消息图片在桌面、320px 窄屏及明暗主题下无横向溢出；点击后进入无边框图片查看，关闭、焦点与键盘行为复用现有查看器契约。
- [ ] AC8：旧消息或没有附件关联的消息继续按纯文本显示；关联仍存在但底层文件不可读取时，消息文字仍正常显示，图片位置提供可感知的失败状态且不会抛出页面错误。
- [ ] AC9：提供 PostgreSQL 迁移并同步 Drizzle journal/snapshot；补充关联约束、发送失败、DTO 恢复、消息渲染、编辑重发与重新生成测试。

## Out Of Scope

- 公开分享页、分享快照和公开附件下载授权。
- 历史消息附件回填或从旧 JSON 字符串自动恢复图片。
- 新增图片格式、修改压缩策略、修改模型视觉能力目录或 Provider 路由语义。
- 非图片文件在消息气泡中的展示与历史复用。
- “继续生成”操作重新注入历史图片；本任务只覆盖普通发送、编辑重发与重新生成，继续生成保持现状。
- 知识库文件生命周期、文件管理页或通用附件库重构。

## Technical Notes

- 优先使用独立的消息与文件关联契约，保持 `messages.content` 的文本语义与现有编辑、复制、分支逻辑稳定。
- 该任务跨数据库、API、聊天 store 和 UI，属于复杂任务，需要 `design.md` 与 `implement.md` 后才能进入实现。
