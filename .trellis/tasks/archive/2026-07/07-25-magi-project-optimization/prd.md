# MAGI 三脑项目优化

## Goal

在本地独立分支 `opt0725` 上，以“审视 -> 执行 -> 提升”为一个大轮次，持续发现并解决 Nekosora 中有明确证据、可独立验证的高价值问题，使项目在不扩大产品范围的前提下获得可靠的质量提升。

## Background

- 起点为 `main` 分支提交 `496432b`，创建任务时工作树干净。
- 当前没有其他活跃 Trellis 任务。
- 用户要求按 MAGI 三脑原则轮流执行：先审视并提出问题，再执行并解决问题，最后复核并给出下一步方向。
- 具体优化模块尚未指定，首轮范围必须通过代码、测试、配置和近期变更证据收敛。
- 基线质量门已通过：`pnpm lint`、`pnpm exec tsc --noEmit --pretty false`、60 个 Vitest 文件共 531 个测试均通过；因此首轮不处理无确定回归证据的工程配置。
- 审视确认 Agent 多工具调用在 `src/lib/stream.ts:849` 将每个调用分别写成一组 assistant/tool 消息；一次返回多个工具调用时，下一轮消息序列不符合 OpenAI 工具调用格式。
- 审视确认网关流式响应在 `src/app/v1/chat/completions/route.ts:98` 创建取消控制器，但 `src/app/v1/chat/completions/route.ts:106` 未把信号传给 `streamChat`，取消后仍可能继续上游生成，并继续写已取消的响应流。

## Requirements

- R1. 所有产品代码变更只发生在本地分支 `opt0725`，不得改写 `main` 历史。
- R2. 每个实施项必须先有可核验的问题证据，包括受影响行为、代码位置和验证方式。
- R3. 优先处理影响核心功能正确性、数据安全、兼容性或可靠性的问题；不得为了“优化”引入未经要求的新功能。
- R4. 每个大轮次严格包含审视、执行、提升三个阶段；执行后的提升阶段必须独立复核实现并记录剩余风险或后续方向。
- R5. 修改应保持最小范围，遵循现有架构、项目规范与测试风格。
- R6. 涉及产品范围、用户体验、兼容性、数据迁移或不可逆行为的决策，必须在实施前取得用户批准。
- R7. Agent 一轮产生多个工具调用时，下一轮请求必须包含一条聚合全部 `tool_calls` 的 assistant 消息，随后按原顺序包含所有对应 tool 结果消息；单工具、工具失败、事件透传和聚合用量行为保持不变。
- R8. `/v1/chat/completions` 流式响应被消费者取消时，必须中止正在进行的 `streamChat`/上游请求，并且不得再写入 `[DONE]`、错误帧或关闭已取消的流；正常完成和正常错误的 SSE 行为保持不变。

## Acceptance Criteria

- [x] AC2. 首轮实施前形成带 `file:line` 证据的问题清单，并明确选择理由、范围和回滚点。
- [x] AC3. 每个已实施问题均有对应的回归测试或等价的可重复验证，验证结果被记录。
- [x] AC4. 独立质量复核未发现未处理的阻断问题；发现的非阻断问题与剩余风险被如实记录。
- [x] AC5. 最终交付说明每轮改了什么、验证了什么、没有验证什么、剩余风险与下一轮建议。
- [x] AC6. 新增回归测试证明两个工具调用只生成一条含两个 `tool_calls` 的 assistant 消息，后接两条顺序一致的 tool 消息，且第二轮能正常完成。
- [x] AC7. 新增路由测试证明取消响应 body 后，传给 `streamChat` 的 `AbortSignal` 变为 aborted，且取消后不产生未处理的流写入异常。
- [x] AC8. `src/lib/stream-agent-loop.test.ts` 与新增网关路由测试通过；改动后的 lint 与 TypeScript 检查通过。

## Out of Scope

- 未经证据支持的全项目重构、依赖升级或视觉改版。
- 新增产品功能或改变既有产品策略。
- 修改 `docs/cankao` 下的参考项目。
- 发布、推送远端分支或创建 PR。
- 首轮不处理 `ChatMessageList` 索引 key、新会话侧栏刷新、非流式错误 HTTP 状态和多模态压缩候选；它们保留为后续轮次，需分别核验完整边界后再规划。
