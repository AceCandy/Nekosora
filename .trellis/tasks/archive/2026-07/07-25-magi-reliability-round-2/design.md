# 公开分享软删除隔离设计

## 边界

本轮只调整 `getShare` 的消息读取条件。分享记录仍保存创建时的消息 ID 快照，软删除仍由既有 `softDeleteMessage` 负责，不修改数据库结构、分享 URL、撤销流程或页面渲染。

## 数据流与契约

1. `getShare(shareId)` 校验分享存在、状态为 active 且未撤销。
2. 从 `messageIdsJson` 读取创建时的消息 ID 顺序。
3. 查询消息时同时约束 `conversationId = share.conversationId` 与 `deletedAt IS NULL`。
4. 仍按快照 ID 顺序映射查询结果；已软删除或不存在的 ID 被跳过。
5. 若快照 ID 非空但所有消息均已删除，返回原分享标题、模型和空消息列表，不把有效分享误判为 404。
6. `lastAccessedAt` 的尽力更新行为保持不变。

## 方案取舍

选择在读取时过滤，而不是在软删除时改写或撤销所有分享。读取时过滤直接执行消息可见性契约，能覆盖现有和未来分享，也不会引入跨表更新、事务或迁移。仅从 `messageIdsJson` 移除 ID 不能消除已有分享的泄露，故不采用。

## 兼容性与回滚

- 对未删除消息、消息顺序、分享元数据和撤销状态无行为变化。
- 已删除消息将立即从旧分享链接消失，这是预期的隐私收紧。
- 无数据库迁移、缓存失效或部署顺序要求。
- 回滚点是 `share.ts` 的单个查询条件及对应测试；回滚会重新暴露缺陷，因此仅用于定位异常。

## 风险

测试使用数据库查询 mock，重点锁定 Drizzle 条件组合与返回映射；全量测试和生产构建负责捕获类型与集成回归。真实 PostgreSQL 的 `IS NULL` 语义由现有 Drizzle 使用方式和创建分享路径共同验证。
