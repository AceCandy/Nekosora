# 模型可见性分组排序

## Goal

让导航入口 `/panel/models` 中唯一管理员的模型列表与聊天端展示顺序一致：私有模型在前、公开模型在后，且每个分组可独立拖拽排序；管理员可在列表中直接切换模型可见性。系统数据库强制只能存在一个管理员账号。

## Background

- 侧边栏只导航到 `/panel/models`；`/admin/models` 无导航入口，本次不作为产品页面改动。
- 管理员访问 `/panel/models` 时，`ModelsManager.tsx` 同时显示私有和公开模型，并允许通过表单修改可见性。
- `reorderMyModels()` 以当前用户的全部模型为一个排序域，允许跨可见性拖拽；`createMyModel()` 也以 owner 全量最大排序值追加。
- `getVisibleModels()` 已按 `sortOrder` 排序，并稳定地将当前用户私有模型置于公开模型之前；聊天 UI 无需新增分组或排序逻辑。
- `user.role` 目前没有数据库唯一约束；未上线环境当前仅有一个管理员，用户明确不要求存量数据兼容或自动修复。

## Requirements

- R0. PostgreSQL 与 SQLite 的 `models.vendor` 字段及全部应用层读写必须删除；`/v1/models.owned_by` 固定为 `nekusora`。
- R0a. 新增数据库模型目录作为模型类型、能力与默认参数的唯一事实来源；模型通过外键引用目录，不再保存独立能力副本。
- R0b. 目录按标准模型名和别名匹配；新增模型匹配成功时自动绑定，管理员也可以显式选择另一条目录记录覆盖自动匹配。
- R0c. 已绑定目录的能力在模型表单中只读，目录修改后所有引用模型实时生效。
- R0d. 流式与非流式支持属于具体路由的探测结果，不写入模型目录。

- R1. 在 PostgreSQL 和 SQLite 中为 `user.role='admin'` 建立 partial unique index，数据库拒绝第二个管理员账号。
- R2. 管理员在 `/panel/models` 按私有、公开两个分组展示模型；私有分组在前，公开分组在后。
- R3. 两个分组的拖拽排序相互隔离，用户不能把模型拖到另一个可见性分组。
- R4. 私有模型排序仅作用于当前 owner 的私有模型；公开模型排序作用于唯一管理员的公开模型。
- R5. 可见性列改为点击式二态控件，显示当前的“私有”或“公开”状态。
- R6. 从私有切换为公开前必须弹出确认对话框，明确告知发布后所有用户可在聊天中选择该模型；从公开切换为私有直接执行。
- R7. 切换可见性后，模型移动到目标分组末尾，并持久化新的 `sortOrder`。
- R8. 发布为公开模型时继续执行名称全局唯一校验，不允许与现有公开模型同名。
- R9. 新建模型可选择初始可见性，并按所选排序域追加到末尾；编辑模型不再提供或接受可见性变更。
- R10. 普通用户的 `/panel/models` 仍只显示自己的私有模型，现有排序、创建、编辑行为不变。

## Acceptance Criteria

- [ ] SQLite 与 PostgreSQL 数据库均拒绝插入或更新出第二条 `role='admin'` 的用户记录。
- [ ] 管理员在 `/panel/models` 同时存在私有和公开模型时，模型按两个明确分组渲染，私有分组始终位于公开分组之前。
- [ ] 在私有分组拖拽后，仅当前 owner 的私有模型 `sortOrder` 被重写为连续整数；公开模型顺序不变。
- [ ] 在公开分组拖拽后，唯一管理员的公开模型 `sortOrder` 按拖拽结果持久化，聊天页展示相同的公开模型相对顺序。
- [ ] 跨分组拖拽不可能发生。
- [ ] 点击私有状态会先显示发布确认；确认后模型成为公开模型并出现在公开分组末尾。
- [ ] 点击公开状态不会弹确认；模型成为私有模型并进入唯一管理员的私有分组末尾。
- [ ] 发布时如与已有公开模型重名，操作失败且模型的可见性及排序不变。
- [ ] 新建私有模型追加到当前 owner 私有组末尾；新建公开模型追加到全局公开组末尾。
- [ ] 编辑模型弹窗不展示可见性选择，`updateMyModel()` 不再修改 `visibility`。
- [ ] 类型检查通过；覆盖唯一管理员、排序和可见性变更约束的测试通过。

## Out Of Scope

- 不修改聊天端组件的分组或渲染结构。
- 不修改未导航的 `/admin/models` 页面及其 actions。
- 不为多管理员存量数据提供迁移、降级或兼容逻辑；未上线环境直接应用唯一约束。

## Notes

- 本次是双数据库 schema、migration、Server Action 和前端交互的跨层改动，需在实施后完整验证。
