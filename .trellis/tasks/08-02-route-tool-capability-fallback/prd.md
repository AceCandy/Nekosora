# 路由工具能力默认开启与自动复标

## Goal

让新建路由默认具备工具调用能力，并在实际请求证明某条路由不兼容工具时自动降级和复标，减少人工维护，同时避免把可恢复的兼容性问题直接暴露给聊天用户。

## Background

- 当前路由默认按“不支持工具”处理，需要人工开启。
- 用户希望反转默认值：默认支持工具，仅对确实不支持的路由人工或自动标记为关闭。
- 用户希望运行时发现工具不兼容时，当前请求能够降级而不是直接报错，并把结果持久化到对应路由。

## Confirmed Facts

- `routes.supports_tools` 是逐路由布尔字段，当前数据库与新增路由默认值均为 `false`；新增路由表单也默认不勾选。
- 该保守默认源于 2API 兼容路由曾把工具调用 JSON 当普通文本返回；用户当时明确要求按实际路由判断能力，但未单独确认永久使用默认关闭策略。
- 模型目录的 `capabilities.tools` 是模型能力上限；运行时还要求具体路由的 `supports_tools=true`。
- WebChat 与 `/v1/chat/completions` 最终共用逐路由执行引擎；每次上游失败时都能获得实际命中的 `routeId`。
- 带工具请求当前会跳过已标记不支持的路由，并尝试下一条支持路由；首个文本、推理或工具调用事件输出后，请求已提交，不能再透明重试。
- 当前错误归一化会丢弃 AI SDK `APICallError.responseBody`，只保留状态码和顶层消息；仅凭 HTTP 400 无法可靠判断工具能力不支持。
- 工具本身的执行失败（例如搜索服务、MCP、参数或网络错误）不能证明模型路由不支持工具。

## Requirements

- 新建路由的工具能力默认值改为“支持”。
- 现有数据库中已经是“不支持工具”的路由保持原值，不做批量回填；这些路由由管理员逐条确认后手动开启。
- 管理端仍允许人工把具体路由标记为“不支持工具”。
- 对已标记为“不支持工具”的路由，请求链不得向上游发送工具相关参数。
- 对标记为“支持工具”但实际返回工具不兼容错误的路由，系统应尝试不带工具参数的降级请求。
- 在降级前优先按现有故障转移规则尝试其他支持工具的路由，避免不必要地丢失工具能力。
- 降级请求最多执行一次，且只在原请求尚未产生可见响应时触发。
- 自动复标必须作用于发生失败的具体路由，不得扩大到同模型的其他路由。
- 自动复标使用原子条件更新，仅把当前仍为“支持工具”的路由改为“不支持工具”；持久化失败不得让当前请求失败。
- 不得把超时、限流、鉴权、内容审核或普通服务端错误误标为“不支持工具”。
- 自动复标仅允许在上游明确拒绝 `tools` / `tool_choice` 时执行 `true -> false`。
- 工具定义发送成功但后续工具执行失败时，不得据此改变模型路由能力。
- 已人工标记为“不支持工具”的路由不得自动重新开启。
- WebChat 与 `/v1/chat/completions` 共用同一套降级与复标行为。

## Acceptance Criteria

- [ ] 新建路由未显式设置工具能力时，读取结果为“支持工具”。
- [ ] 迁移不会修改既有 `supports_tools=false` 行。
- [ ] 管理员可显式保存并读取“不支持工具”状态。
- [ ] 已关闭工具能力的路由不会收到工具相关请求参数。
- [ ] 首条支持工具路由明确拒绝工具时，系统记录该路由的失败并继续尝试下一支持工具路由。
- [ ] 可确认的工具不兼容错误能把实际路由标记为关闭，并在没有其他可用工具路由且尚未输出内容时触发一次无工具降级。
- [ ] 降级请求不包含 `tools`，不会造成无限重试或重复工具执行。
- [ ] 自动复标只更新实际命中的路由。
- [ ] 非工具兼容性错误保持现有错误处理，不触发复标。
- [ ] 工具执行返回错误结果时不触发复标。
- [ ] 数据库、服务端契约和管理端状态往返一致。

## Out of Scope

- 不自动探测或批量扫描所有历史路由。
- 不基于模型名称猜测工具能力。
- 不识别“模型返回工具 JSON 但 HTTP 成功”的静默协议不兼容；该类问题仍需人工标记或后续独立探测方案。
- 不自动把“不支持工具”路由重新标记为支持。
- 不改变与工具兼容性无关的路由熔断、限流或重试策略。
