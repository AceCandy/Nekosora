# Chat 导航与客户端负载治理

## Goal

让会话数量增长时 Chat 首屏和侧栏保持有界加载，并基于实际包体/渲染证据收敛重型客户端依赖。

## Background

- `apps/web/src/features/chat/actions/conversations.ts:107` 的会话导航查询未提供分页窗口。
- `apps/web/src/app/chat/layout.tsx:20` 在根布局加载完整会话列表并序列化给客户端侧栏。
- 重型 Markdown/Artifact 客户端依赖属于待测规模风险，不能在缺少生产构建数据时直接判定必须拆分。

## Requirements

- R1. 会话侧栏采用服务端分页或游标窗口，初始 RSC payload 不再随用户全部会话线性增长。
- R2. 保持现有排序、当前会话定位、创建/删除/重命名和移动端抽屉行为；搜索若需要全量结果，应使用独立服务端查询。
- R3. 分页状态必须处理重复、删除、并发新增和到达末尾，不能依赖客户端全量去重掩盖服务端不稳定游标。
- R4. 在修改 Markdown、Mermaid、Shiki、Artifact 的加载边界前先记录生产构建包体和交互基线；只有存在可测收益时才采用动态加载。
- R5. 不引入 React Query/SWR，不对聊天消息列表增加与现有滚动契约冲突的虚拟滚动。
- R6. 浏览器验证覆盖桌面和 390px 移动端的加载、键盘操作、当前项可见性和慢网络状态。

## Acceptance Criteria

- [ ] 首屏会话查询和序列化数量有固定上限，继续加载不会出现重复或丢项。
- [ ] 当前会话和常用导航操作在分页后保持一致。
- [ ] 客户端拆分只有在包体或加载证据证明改善时落地；无收益则保留现状并记录结论。
- [ ] 定向测试、浏览器回归、`pnpm check`、`pnpm test` 与独立复核通过。

## Out Of Scope

- 恢复暗色主题。
- 虚拟化聊天消息正文或重写 Chat Composer 状态架构。
