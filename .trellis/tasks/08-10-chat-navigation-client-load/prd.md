# Chat 导航与客户端负载治理

## Goal

让会话数量增长时 Chat 首屏和侧栏保持有界加载，并基于实际包体/渲染证据收敛重型客户端依赖。

## Background

- `apps/web/src/features/chat/actions/conversations.ts:107` 的会话导航查询仅按 `updatedAt DESC` 排序，未提供稳定次序或分页窗口。
- `apps/web/src/app/chat/layout.tsx:20` 在 Chat 布局加载完整会话列表并序列化给客户端侧栏；`getGeneratingStatuses` 同样扫描全部会话。
- 侧栏当前按“未归档置顶、未归档时间分组、归档”展示，并通过 Zustand 乐观补入新会话；消息搜索已经是独立服务端查询，限制为 50 条。
- Artifact 代码高亮、Mermaid 和结构化图表已有按需加载边界；现有生产产物不足以证明拆分核心 Markdown 渲染器有净收益。

## Requirements

- R1. 会话侧栏首屏最多加载 30 条，使用与当前分组一致的服务端键集游标；初始 RSC payload 不再随用户全部会话线性增长。
- R2. 保持现有分组顺序、当前会话定位、创建、删除、重命名、置顶、归档和移动端抽屉行为；当前深链会话不在首屏窗口时必须按 ID 安全补入。
- R3. 游标以服务端完整排序键为边界，使用不可变 `id` 打破相同更新时间并列；加载更多必须处理删除、并发新增、重复请求和末尾状态。
- R4. 保留现有独立服务端消息搜索及 50 条上限，不将搜索结果限制在已加载的侧栏窗口。
- R5. 将生成状态轮询改为只返回当前用户仍有效的活动 run；轮询启动不能依赖活动会话是否落在首屏 30 条内。
- R6. 记录当前 Markdown、Mermaid、Shiki、Artifact 加载边界和生产产物基线；本任务不拆分核心 Markdown，除非实现阶段得到可归因且可复测的收益证据。
- R7. 不引入 React Query/SWR，不对聊天消息列表增加与现有滚动契约冲突的虚拟滚动。
- R8. 浏览器验证覆盖桌面和 390px 移动端的加载、键盘操作、当前项可见性和慢网络状态。

## Acceptance Criteria

- [x] 首屏常规窗口最多 30 条；分页查询使用完整稳定排序与匹配索引，继续加载不会因相同 `updatedAt`、删除或重复请求出现重复或漏掉既有项。
- [ ] 深链当前会话不在首屏时仍可见且高亮；创建、删除、重命名、置顶、归档、搜索和移动抽屉行为保持一致。（代码与测试已覆盖；缺少登录态浏览器回归。）
- [x] 生成状态轮询只读取有效活动 run，不再返回用户全部会话状态；活动会话位于后页或由客户端新建时仍会持续跟踪。
- [x] 已有动态加载边界与生产产物规模被记录；核心 Markdown 保持现状，并写明缺少可靠归因数据的延期条件。
- [ ] 定向测试、浏览器回归、`pnpm check`、`pnpm test` 与独立复核通过。（除登录态浏览器回归外均通过。）

## Verification Record

- `pnpm check`、`pnpm test`、`pnpm --filter @nekusora/web build`、`git diff --check` 已通过。
- 独立复核发现并修正了新会话本地流开始后轮询不启动、空活动集合后仍续排定时器，以及游标谓词测试过弱的问题。
- 未拆分 Streamdown/Markdown：现有产物缺少可归因的 route bundle 数据，无法证明拆分有净收益。
- 未验证：受保护 Sidebar 的登录态桌面与 390px 交互。隔离浏览器只能验证 `/chat` 重定向登录页；未读取或绕过用户凭据。
- 任务外既有问题：登录提交按钮对比度约 3.81:1，低于 WCAG 4.5:1，本任务未修改。

## Out Of Scope

- 恢复暗色主题。
- 虚拟化聊天消息正文或重写 Chat Composer 状态架构。
- 分页聊天消息正文、改造全文搜索实现或引入新的客户端请求状态库。
